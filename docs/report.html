01 조사

먼저 알아야 했던 것

설계보다 조사가 먼저였다. 나무위키의 공식 DB 덤프는 2021년 3월이 마지막이고 5년째 갱신이 없다. 커뮤니티 덤프도 2022년이 최신이라, 현재 실질 문서의 46%밖에 덮지 못한다. "최신까지 전부"를 원한다면 크롤링이 필수다.

그런데 robots.txt를 실제로 열어보니 예상과 달랐다. 문서 본문 경로 /w/가 허용되어 있었고, Cloudflare 챌린지 없이 정상 응답했다. 다만 나무위키 측은 "크롤링은 서버 부담이니 덤프를 받으라"고 안내한다 — 허용은 됐지만 환영받는 건 아니라서, 보호 장치를 정책이 아니라 코드로 강제했다.

가장 중요한 발견은 /sidebar.json이었다. robots.txt가 명시적으로 허용한 엔드포인트인데 최근 변경을 JSON으로 준다. 항목 15개가 약 32초를 덮는 슬라이딩 윈도우라, 폴링 주기가 30초를 넘으면 그 사이 편집이 영구 유실된다. 이 한 줄이 신선도 설계 전체를 결정했다.

03 구조

만든 것

각 단계는 Kafka 토픽으로만 통신하고 서로를 직접 호출하지 않는다. 문서 본문은 최대 16만 자라 메시지에 넣을 수 없으므로, 본문은 블롭 저장소에 두고 Kafka에는 참조만 흘린다(클레임 체크). 이 설계가 재크롤 없는 재파싱과 재파싱 없는 재임베딩을 가능하게 한다.

frontier → crawl.requests sidebar.json 10초 폴링 · 재방문 스케줄
crawler → docs.raw 동시 4 · 서킷 브레이커 · 링크 BFS
parser → chunks.ready 앵커 기반 추출 · 수율 카나리아
embedder → Qdrant dense + sparse · 유일한 진짜 병목
api RRF + rerank 하이브리드 검색 · 그래프 확장

docs.raw와 chunks.ready는 compact 정책으로 영구 보존한다. 파서를 고치면 docs.raw를, 임베딩 모델을 바꾸면 chunks.ready를 오프셋 0부터 재생하면 된다.

분산이 실제로 의미 있는 구간

정직하게 말하면 네 단계 중 하나만 진짜 분산 문제다. 크롤은 상대 서버를 배려해야 해서 노드를 늘리면 안 되고, 파싱은 14코어로 충분하다. 오직 임베딩과 벡터 인덱스만 노드를 추가할수록 선형으로 빨라진다. 크롤러를 컨슈머 그룹으로 만든 건 성능이 아니라 장애 격리 때문이다.

04 함정

구현 중 실제로 터진 것

전부 조용히 실패하는 종류였다. 로그에 아무것도 안 남거나, 남더라도 원인과 무관한 증상만 보였다.

증상진짜 원인대응
컨슈머 그룹이 0건만 반환 kafka-python이 Python 3.14의 selectors와 비호환. 그룹 없는 소비는 되고 그룹 소비만 실패 confluent-kafka로 교체
저장된 파일이 HTML이 아님 Accept-Encoding에 br을 직접 넣었는데 brotli 디코더가 없어 압축 바이너리가 그대로 저장 헤더를 직접 지정하지 않음 + HTML 검증 가드
머신 전체가 느려짐 SPLADE 로짓 (16 × 512 × 250,002) 텐서를 세 벌 만들어 RAM 8.7GB 점유 단조성을 이용해 풀링 후 변환 → 한 벌로. 배치도 축소
문서 15건 색인 실패 추출 텍스트의 NUL(0x00) — PostgreSQL text가 거부 추출 단계에서 제어문자 제거
크롤 요청 전부 실패 User-Agent에 한글 — HTTP 헤더는 ASCII만 허용 UA를 ASCII로
두 번째 배치부터 크래시 asyncio.Lock이 asyncio.run()마다 새로 생기는 루프에 묶임 락 없는 슬롯 예약 방식
카나리아가 영영 재검증 안 됨 문서가 안 바뀌면 "변경 없음" 단축 경로를 타서 검사 자체가 실행되지 않음 카나리아 문서는 단축 경로 예외

추출기는 언젠가 조용히 깨진다

나무위키의 CSS 클래스명은 빌드 해시(_0MSSsdmG)라 배포마다 바뀐다. 그래서 셀렉터를 일절 쓰지 않고 의미론적 앵커만 쓴다 — id="s-4.1" 형태의 섹션 앵커(점 표기가 곧 헤딩 계층), <details><summary> 네비게이션 틀, 라이선스 고지문. 이 앵커들은 외부 링크와 법적 의무 때문에 함부로 바뀌지 않는다.

그럼에도 언젠가 깨지므로, 기준 문서 5개의 추출 길이를 감시해 ±30% 이탈 시 경보하고 파서를 정지시킨다. 이게 없으면 빈 문자열로 900만 청크를 오염시켜도 알아채지 못한다.

05 신선도

하루 33,600개가 바뀐다

코퍼스의 2.7%가 매일 갱신된다. 3층으로 대응한다.

층방식지연역할
1. 실시간sidebar.json 10초 폴링초편집 즉시 큐잉
2. 재방문next_due_at 14일최대 14일1층이 놓친 것 회수
3. 차단content_hash 비교—불필요한 재임베딩 제거

3층이 비용을 좌우한다. 이게 없으면 14일 주기 재방문마다 코퍼스 전체를 재임베딩하게 된다. 삭제·이동된 문서는 404를 만나면 tombstone을 흘려 Postgres와 Qdrant에서 제거한다.

전수 크롤에 70시간이 걸리는 동안에도 약 10만 문서가 바뀐다. 일관된 스냅샷은 원리적으로 불가능하다. 그래서 감추는 대신 드러낸다 — 검색 결과마다 문서의 최근 수정 시각과 수집 시각을 함께 표시한다.

06 지식그래프

이미 절반은 쌓이고 있었다

나무위키는 링크와 분류 덕분에 그 자체로 지식그래프다. DBpedia가 위키백과로 한 것과 같은 구조다. 재료는 수집 과정에서 이미 나오고 있었고, 저장만 안 하고 있었다.

단계내용상태
KG-1 문서 그래프 — 링크·분류·이웃 확장 검색·PageRank 완료
KG-2 엔티티·관계 추출 — 청크에서 트리플 추출. 전량은 수백 시간이라 PageRank 상위 5만 문서부터 예정
KG-3 커뮤니티 요약 — 그래프 클러스터링 + 계층 요약으로 전역 질의 대응 예정

엣지는 최종적으로 약 10억 개가 예상된다. 별도 엣지 테이블은 sha1 40자 × 2 × 10억 = 80GB로 과해서, TEXT[] 배열 + GIN 인덱스로 뒀다. TOAST 압축이 먹고 역링크 질의도 된다.

KG-3의 함정을 미리 못 박아둔다: 하루 33,600개가 바뀌는 코퍼스에서 커뮤니티 요약을 매번 전부 다시 만들 수는 없다. 변경된 커뮤니티만 무효화하는 증분 갱신을 처음부터 설계에 넣지 않으면 KG-3은 유지 불가능해진다.

07 검증

색인이 채워지자 달라진 것

색인이 18%였을 때와 100%일 때 같은 질의를 돌린 결과다. 리랭커 점수가 답이 있는지 없는지를 정확히 반영한다 — 색인에 답이 없으면 0.15~0.19로 떨어지고, 있으면 0.96~1.00으로 올라간다.

질의색인 18%색인 100%
파이썬은 어떤 언어인가 0.192 — 과학고등학교 › 교과목 0.998 — Python › 개요
축구 경기 규칙 0.150 — 대한민국/스포츠 › K리그 0.965 — 축구 › 규칙
부산의 지리적 특징 0.371 — 중구(부산) › 지역 특징 0.998 — 부산광역시 › 지리 > 도시구조 > 특징
김연아 올림픽 메달 0.998 0.998

부산 질의의 헤딩 경로가 지리 > 도시구조 > 특징으로 정확히 짚혔다 — 청크 앞에 헤딩 경로를 접두로 붙인 설계(§5.1)가 값을 한 지점이다. 파이썬으로 물어도 Python 문서가 나오는 것은 리다이렉트 접기 덕이다.

남은 품질 문제

축구 경기 규칙 1위 결과에 네비게이션 박스가 새어 들어왔다 — 영국군 부대 목록("전략사령부 · 근위대 · 제22SAS연대…")이 본문으로 잡혔다. 추출기는 <details><summary>펼치기·접기</summary> 형태의 네비박스를 제거하는데, 그 형태가 아닌 네비박스가 남는다. 점수는 0.965로 높게 나오지만 내용은 질의와 무관하다.
