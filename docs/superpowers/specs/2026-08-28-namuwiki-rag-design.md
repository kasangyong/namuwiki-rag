# 나무위키 분산 수집·RAG 검색 시스템 설계

- 작성일: 2026-08-28
- 상태: 설계 확정 대기
- 목표 환경: 단일 노트북 (i7-13700H 14코어 / RAM 32GB / RTX 4050 6GB / 디스크 545GB 여유) → 추후 다중 노드

---

## 1. 목표와 비목표

### 목표

1. 나무위키 전체 문서를 수집하고 최신 상태로 유지한다.
2. 수집·파싱·임베딩·색인이 **각각 독립적으로 스케일아웃되는 분산 파이프라인**을 구축한다.
3. 자연어 질의에 대해 근거 문단을 검색하고 답변을 생성한다 (RAG).

### 명시적 비목표

- **상업적 이용.** 나무위키는 CC BY-NC-SA 2.0 KR이므로 비영리로만 사용한다.
- **성능 최적화를 위한 분산.** 분산은 학습 목적이다. 단일 노드가 더 빠른 구간에서도 분산 구조를 유지하되, 그 사실을 문서에 명시한다.
- 이미지·파일 이름공간(571만 개) 수집. 텍스트만 다룬다.
- 나무위키 원본 마크업(namumark) 파서 구현. 렌더링된 HTML에서 추출한다.

### 설계 원칙

- 각 단계는 Kafka 토픽으로만 통신한다. 서비스 간 직접 호출을 금지한다.
- 모든 단계는 **멱등**하다. 어디서 재시작해도 결과가 같다.
- 재수집 없이 재파싱, 재파싱 없이 재임베딩이 가능해야 한다.
- 외부 사이트의 CSS 클래스명·DOM 구조에 의존하지 않는다.

### 2.5 접근 정책 및 엔드포인트

`https://namu.wiki/robots.txt` 실측:

```
User-agent: *
Disallow: /
Allow: /$
Allow: /w/              ← 문서 본문
Allow: /history/
Allow: /backlink/
Allow: /RecentChanges
Allow: /Search
Allow: /sidebar.json    ← 최근 변경 JSON
Allow: /OrphanedPages, /UncategorizedPages, /ShortestPages, /LongestPages
...
```

- **문서 본문(`/w/`) 크롤은 robots.txt상 허용**된다. Cloudflare 챌린지 없이 HTTP 200으로 응답한다.
- `sitemap.xml`은 **존재하지 않는다** (404).
- 나무위키는 "크롤링은 서버 부담이니 DB 덤프를 권장한다"고 안내한다. → 속도 제한과 식별 가능한 User-Agent를 필수 요건으로 삼는다.
- `/RecentChanges`는 **JS 렌더링 SPA**라 서버 응답에 내용이 없다. 대신 `/sidebar.json`이 동일 정보를 JSON으로 준다.

**`/sidebar.json` 구조** (핵심 발견):

```json
[{"document":"판타지 파티/2025년","status":"normal","date":1787905921}, ...]
```

- 항목 **15개 고정**, 시간 범위 **약 32초**
- → **폴링 주기가 30초를 넘으면 편집을 놓친다. 10초 주기로 고정한다** (3배 안전 여유, 8,640 req/일로 부하 무시 가능)

### 2.7 HTML 구조

크롤한 HTML을 분석한 결과 두 가지 상반된 사실이 나왔다.

**나쁜 소식 — CSS 클래스명이 난독화되어 있다:**

```html
<div class="_0MSSsdmG">&nbsp;</div>
<div class="_7+ybbnyU o43ZfaJi" data-v-cc904084>
```

빌드 해시 기반이므로 **프론트엔드 배포 때마다 바뀐다.** 클래스 셀렉터에 의존하는 추출기는 예고 없이 조용히 깨진다.

**좋은 소식 — 섹션 앵커는 의미론적이고 안정적이다:**

```html
<h2 id="s-4"   href="#toc">4. 수상 기록 [편집]</h2>
<h3 id="s-4.1" href="#toc">4.1. 수훈 [편집]</h3>
```

`id="s-4.1"` 형태의 **계층적 섹션 ID**가 있다. 점 표기가 곧 헤딩 계층이다. 이 앵커는 `#s-4` 형태로 외부 링크에서 참조되므로 함부로 바꿀 수 없다 — 구조적으로 안정적이다.

> **추출 규칙: `id="s-N[.M...]"` 앵커와 `<h1>~<h6>` 태그만 사용한다. CSS 클래스는 절대 사용하지 않는다.**

**내부 링크 밀도:** 문서당 `/w/` 내부 링크가 **1,000~1,500개** (대한민국 1,525 / 김연아 1,053). 링크 BFS로 전체 문서 그래프를 덮는 것이 충분히 현실적이다.

| dragonkue/bge-reranker-v2-m3-ko | 0.5B | 0.8089 |

**이 데이터에서 도출한 세 가지 결론:**

1. **BGE-M3 단독 설계는 기각한다.** BGE-M3의 dense 성능(0.7483)은 같은 0.5B 그룹에서 최하위권이다. KURE-v1(+1.6%p), PIXIE-Rune-Preview(+2.2%p)가 더 낫다.

   BGE-M3를 고려했던 유일한 이유는 dense·sparse·colbert 3헤드를 한 모델이 제공한다는 점이었다. 확인 결과 `nlpai-lab/KURE-v1` 저장소에는 `sparse_linear.pt`·`colbert_linear.pt`가 **없다** (dense 전용). 반면 `BAAI/bge-m3`에는 둘 다 있다. 즉 KURE의 dense 이득을 얻으려면 sparse를 따로 마련해야 한다.

   그런데 sparse를 따로 두는 비용이 작다: **PIXIE-Splade-v1.5는 0.1B**에 불과하면서 BM25보다 **26%p** 앞선다. 0.5B dense + 0.1B sparse 조합의 추가 연산은 단일 0.5B 대비 약 1.2배에 그친다.

2. **리랭커를 반드시 넣는다.** dense 최고 0.7882 → 리랭킹 0.8168로 **+3.5%p**. 리랭커는 질의 시점에만 상위 100개에 대해 돌므로 색인 비용이 0이다. 비용 대비 효과가 가장 큰 구성요소다.

3. **⚠ 이 벤치마크 수치를 그대로 믿지 않는다.** 세 표 모두 telepix 모델이 1위다. 벤치마크 저장소 관리자(BM-K)와 TelePIX사의 관계를 확인하려 했으나 명확히 분리 검증되지 않았다. 벤치마크 과적합 가능성이 있다.

   → **완화책: Phase 0에서 나무위키 질의로 직접 A/B 평가한 뒤 모델을 확정한다.** 900만 청크 임베딩에 수십 시간이 드는데, 1시간짜리 자체 평가로 모델을 고르는 것은 명백히 남는 장사다. 임베더는 모델 ID를 설정으로 주입받는 구조로 만든다.

라이선스: KURE-v1 MIT / telepix PIXIE 전 모델 Apache 2.0 / BAAI bge-* MIT·Apache 2.0. **전부 무료·상업적 제약 없음** (단, 데이터 자체가 NC이므로 서비스는 비영리).

## 3. 아키텍처

```
                                          ┌──────────────────┐
   heegyu/namuwiki-extracted ────────────▶│  seed-loader     │  1회성
   (제목 565K + 개발 픽스처)               │  제목만 추출      │
                                          └────────┬─────────┘
                                                   │
   /sidebar.json (10초 폴링) ──────┐                │
                                  ▼                ▼
                          ┌────────────────────────────┐
                          │        frontier            │   Postgres
                          │  제목 큐 · 우선순위 · 상태   │   crawl_state
                          └─────────────┬──────────────┘
                                        │
                                 [crawl.requests] (6 파티션)
                                        │
                          ┌─────────────▼──────────────┐
                          │      crawler × N           │  동시 4~8
                          │  GET /w/ · 링크 수확        │  robots 준수
                          └─────────────┬──────────────┘
                                        │ ├──▶ 신규 링크 → frontier (BFS)
                                        │ └──▶ gzip HTML → BlobStore
                                        │
                                  [docs.raw] (6 파티션, compact, 영구)
                                        │
                          ┌─────────────▼──────────────┐
                          │      parser × N            │  s-N.M 앵커 기반
                          │  HTML → 섹션 → 청크         │  CSS 의존 금지
                          └─────────────┬──────────────┘
                                        │ ──▶ Postgres (documents, chunks)
                                        │
                                 [chunks.ready] (12 파티션, compact, 영구)
                                        │
                          ┌─────────────▼──────────────┐
                          │      embedder × N (GPU)    │  ★ 진짜 병목
                          │  dense 0.5B + sparse 0.1B  │
                          └─────────────┬──────────────┘
                                        │
                                 ┌──────▼──────┐
                                 │   Qdrant    │  dense + sparse
                                 └──────┬──────┘
                                        │
   web UI ──▶ api (FastAPI) ────────────┘
                 │  1) 하이브리드 검색 (RRF)
                 │  2) 리랭킹 (bge-reranker-v2-m3, top-100 → top-8)
                 └─ 3) 답변 생성 (로컬 LLM / 교체 가능)
```

### 3.1 왜 스트리밍인가 (배치 대안 기각 사유)

Airflow/Spark 기반 배치 DAG는 단계마다 배리어가 생긴다. 크롤이 31~61시간 걸리는데 그동안 GPU가 논다. 스트리밍 구조에서는 크롤러가 첫 문서를 넣는 순간부터 임베더가 소비를 시작한다.

또한 Spark의 셔플·파티셔닝은 이 워크로드에 쓸 데가 없다. 파싱은 문서 단위로 완전히 독립적이라 셔플이 발생하지 않으며, 124만 건 파싱은 14코어 멀티프로세싱으로 2~4시간이면 끝난다. Spark를 넣으면 학습은 되지만 파이프라인은 느려진다.

### 3.2 분산의 정당성 (정직한 평가)

| 단계 | 병목 유형 | 노드 추가 효과 |
|---|---|---|
| 크롤 | 네트워크 대기 + **상대 서버 배려** | ❌ 없음. 오히려 늘리면 안 됨 |
| 파싱 | CPU | △ 단일 노드 14코어로 충분 |
| **임베딩** | **GPU** | ✅ **선형 개선. 이것이 유일한 진짜 분산 문제** |
| 벡터 검색 | 메모리 + CPU | ✅ 샤딩 필요 |

크롤러를 컨슈머 그룹으로 만드는 것은 성능이 아니라 **장애 격리와 재시작 용이성** 때문이다. 이 점을 문서에 남겨 "분산했으니 빨라진다"는 오해를 방지한다.

## 4. 데이터 수집 전략

### 4.1 덤프의 역할 재정의

§2.6에서 확인한 대로 덤프는 콘텐츠 소스로 부적합하다. 역할을 둘로 한정한다:

1. **제목 시드**: 565,293개 제목을 `crawl_state`에 초기 적재. BFS 출발점.
2. **개발 픽스처**: Phase 1에서 크롤 없이 파이프라인을 개발·튜닝하기 위한 1만 건 샘플.

덤프에서 온 청크는 `source='dump'`로 표시하고, 같은 문서를 크롤한 순간 **크롤본이 덮어쓴다**. 두 갈래 콘텐츠 경로를 유지하지 않는다.

### 4.2 문서 열거 (Frontier)

전체 124만 문서 목록을 얻는 단일 API가 없으므로 세 경로를 합친다:

| 경로 | 기여 | 방식 |
|---|---|---|
| **덤프 시드** | 565K | 1회성 적재 |
| **링크 BFS** | 나머지 ~675K | 크롤한 페이지에서 `/w/` 링크 1,000~1,500개 수확 → 미방문분 큐잉 |
| **sidebar.json** | 실시간 신규·변경 | 10초 폴링 |
| 분류 페이지 | 보조 | 고아 문서 보정용 |

BFS 수렴성: 565K 시드 × 평균 1,200 링크 = 6.8억 링크 참조. 위키 링크 그래프는 밀도가 높아 소수 홉 안에 대부분을 덮을 것으로 예상한다. **Phase 2에서 신규 발견율이 1% 미만으로 떨어지는 시점을 수렴 판정 기준으로 삼는다.**

### 4.3 크롤 정책

상대 서버가 명시적으로 "크롤링은 부담"이라고 밝혔으므로 다음을 강제한다:

| 항목 | 값 | 근거 |
|---|---|---|
| 동시 요청 | **4** (초기), 최대 8 | 61시간 → 31시간. 8을 넘기지 않는다 |
| 요청 간 지연 | 도메인 전역 최소 100ms | — |
| User-Agent | 연락처 URL 포함 식별자 | 차단 시 상대가 소통할 수 있게 |
| 준수 대상 | robots.txt Allow 경로만 | `/w/`, `/sidebar.json`, `/backlink/` |
| 재시도 | 지수 백오프, 최대 3회 | 429/5xx 시 |
| **서킷 브레이커** | **429 또는 5xx가 1분간 10회 → 10분 정지** | 상대 서버 보호 |
| 조건부 요청 | `If-None-Match` / `If-Modified-Since` | 지원 시 트래픽 절감 |

`/history/`, `/Search`, 사용자 문서는 크롤하지 않는다.

### 4.4 재개 가능성

`crawl_state` 테이블이 단일 진실 원천이다. 프로세스가 죽어도 다음 재시작에서 `next_due_at <= now()`인 항목부터 이어간다. Kafka `crawl.requests`는 7일 보존이며, 유실되어도 `crawl_state`에서 재생성 가능하다.

## 5. 데이터 모델

### 5.1 Kafka 토픽

모든 토픽의 키는 `doc_id = sha1(정규화된 제목)`이다. 같은 문서가 항상 같은 파티션으로 가므로 순서가 보장되고, 구버전이 신버전을 덮어쓰는 사고가 원천 차단된다.

| 토픽 | 파티션 | 보존 정책 | 목적 |
|---|---:|---|---|
| `crawl.requests` | 6 | 7일 삭제 | 작업 큐 |
| `docs.raw` | 6 | **compact, 영구** | 재파싱 원천 |
| `chunks.ready` | **12** | **compact, 영구** | 재임베딩 원천 |
| `crawl.dlq` / `parse.dlq` / `embed.dlq` | 1 | 30일 | 실패 격리 |

`chunks.ready`가 12파티션인 이유: 컨슈머 그룹은 파티션 수를 넘어 확장되지 않는다. 임베더가 유일한 진짜 병목이므로 **장래 GPU 노드 확장 상한을 여기서 12로 설정**한다.

**`docs.raw` 메시지** (클레임 체크 — 본문은 참조로):

```json
{
  "doc_id":       "a3f1c9…",
  "title":        "대한민국",
  "source":       "crawl" | "dump",
  "fetched_at":   "2026-08-28T08:13:06Z",
  "content_hash": "sha256(추출 텍스트)",
  "blob_ref":     "blob://ht/a3/a3f1c9….html.gz",
  "http_status":  200,
  "byte_size":    1973563
}
```

문서 본문은 최대 16만 자로 Kafka 기본 한도(1MB)를 넘을 수 있으므로 반드시 참조로 전달한다.

**`chunks.ready` 메시지** (청크는 1~2KB이므로 인라인):

```json
{
  "chunk_id":     "a3f1c9…:0007",
  "doc_id":       "a3f1c9…",
  "seq":          7,
  "section_id":   "s-4.1",
  "heading_path": ["수상 기록", "수훈"],
  "text":         "대한민국 > 수상 기록 > 수훈\n2010년…",
  "char_len":     842,
  "content_hash": "sha256(text)"
}
```

`text` 앞에 **헤딩 경로를 붙이는 것은 의도적**이다. "수훈" 청크만 떼면 어느 문서인지 알 수 없지만, `대한민국 > 수상 기록 >` 접두가 있으면 임베딩 벡터 자체가 문맥을 갖는다.

### 5.2 PostgreSQL

```sql
CREATE TABLE documents (
  doc_id        TEXT PRIMARY KEY,
  title         TEXT NOT NULL UNIQUE,
  source        TEXT NOT NULL,             -- 'crawl' | 'dump'
  content_hash  TEXT NOT NULL,
  blob_ref      TEXT,
  char_len      INT,
  fetched_at    TIMESTAMPTZ NOT NULL,
  parsed_at     TIMESTAMPTZ,
  is_redirect   BOOLEAN DEFAULT FALSE,
  categories    TEXT[]
);

CREATE TABLE chunks (
  chunk_id      TEXT PRIMARY KEY,
  doc_id        TEXT NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
  seq           INT  NOT NULL,
  section_id    TEXT,
  heading_path  TEXT[],
  text          TEXT NOT NULL,
  content_hash  TEXT NOT NULL,
  embedded_at   TIMESTAMPTZ,
  UNIQUE (doc_id, seq)
);
CREATE INDEX ON chunks (doc_id);
CREATE INDEX ON chunks (embedded_at) WHERE embedded_at IS NULL;

CREATE TABLE crawl_state (
  doc_id        TEXT PRIMARY KEY,
  title         TEXT NOT NULL UNIQUE,
  discovered_by TEXT,                      -- 'dump' | 'bfs' | 'sidebar' | 'category'
  last_fetched  TIMESTAMPTZ,
  last_hash     TEXT,
  etag          TEXT,
  http_status   INT,
  fail_count    INT DEFAULT 0,
  priority      INT DEFAULT 100,           -- 낮을수록 우선
  next_due_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON crawl_state (next_due_at) WHERE fail_count < 5;
```

`documents.categories`는 분류 이름공간(232,870개)에서 얻는 값으로, 검색 시 메타데이터 필터로 활용한다 (예: "1990년대 영화 중에서만 검색").

### 5.3 Qdrant

```
collection: namuwiki_chunks
  vectors:
    dense:  { size: 1024, distance: Cosine, on_disk: true,
              quantization: { scalar: { type: int8, always_ram: true } } }
  sparse_vectors:
    lexical: { }                       # SPLADE 출력
  payload:
    doc_id, chunk_id, title, heading_path, seq, categories
  shard_number: 4                      # Phase 3 다중 노드 대비
```

**용량 산정 (900만 청크 기준):**

| 항목 | 크기 |
|---|---:|
| dense float32 원본 | 36.9 GB (디스크) |
| dense int8 양자화 (RAM 상주) | **9.2 GB** |
| sparse (평균 non-zero 100항) | ~7.2 GB |
| payload | ~4 GB |

int8 스칼라 양자화로 RAM 상주분을 9.2GB로 낮추고 원본은 디스크에 둔다. 32GB RAM에서 감당 가능하다.

|---|---:|
| Qdrant | 10 GB |
| Kafka | 4 GB |
| PostgreSQL | 4 GB |

### 5.5 블롭 저장소 (BlobStore)

**인터페이스만 고정하고 구현은 단계별로 교체한다.**

```python
class BlobStore(Protocol):
    def put(self, key: str, data: bytes) -> str: ...   # returns blob_ref
    def get(self, ref: str) -> bytes: ...
```

| Phase | 구현 | 근거 |
|---|---|---|
| 1~2 | **로컬 파일시스템** (2단계 샤딩 `ht/a3/a3f1c9….html.gz`) | 단일 노드에서 가장 단순하고 빠르다. 45~91 GiB, 디스크 여유 545GB |
| 3 | **SeaweedFS** (S3 API) | 다중 노드 확장 시점에 교체. 소형 파일 다수에 특화 |

MinIO는 2026-02-12 저장소 아카이브로 **채택하지 않는다**.

> **정직한 평가:** 오브젝트 스토리지는 이 설계에서 필요성 논거가 가장 약한 구성요소다. 단일 노드에서는 파일시스템이 모든 면에서 낫다. Phase 3에서 두 번째 노드를 붙일 때 비로소 값을 한다. 인터페이스를 추상화해 두었으므로 교체는 파일 한 개 수정이다.

## 6. 텍스트 추출과 청킹

### 6.1 추출 규칙 (CSS 비의존)

1. `<script>`, `<style>`, `<svg>` 제거.
2. `id="s-N[.M…]"` 앵커와 `<h1>~<h6>`로 섹션 경계를 잡는다. **CSS 클래스 셀렉터 사용 금지.**
3. 섹션 ID의 점 표기에서 헤딩 계층을 복원한다 (`s-4.1` → depth 2, 부모 `s-4`).
4. 본문 범위: 첫 섹션 앵커부터 라이선스 고지문(`이 저작물은 CC BY-NC-SA 2.0 KR에 따라 이용할 수 있습니다`) 직전까지. 이 문구는 CSS와 무관한 안정적 텍스트 랜드마크다.
5. `[편집]`, `&nbsp;` 스페이서, 각주 마커를 정규화한다.
6. 광고 블록 제거 (통계 페이지 실측에서 본문에 광고 텍스트가 섞여 나오는 것을 확인했다).

### 6.2 추출 수율 카나리아 (필수)

난독화된 클래스명 때문에 추출기는 **언젠가 조용히 깨진다.** 침묵 실패를 막기 위한 감시를 파이프라인에 내장한다:

- 고정된 검증용 문서 20개를 매일 재추출한다.
- 기대 텍스트 길이 대비 **±30% 이탈 시 경보**하고 파서 컨슈머를 정지한다.
- 전체 추출 텍스트/HTML 비율(기준 1:13.7)의 이동평균을 모니터링한다.

이 장치가 없으면 파서가 빈 문자열을 뱉으며 900만 청크를 오염시켜도 알아채지 못한다.

### 6.3 청킹

| 항목 | 값 |
|---|---|
| 단위 | 섹션 내부에서 문단 경계 우선 분할 |
| 목표 크기 | 512 토큰 ≈ **850자** (한국어 XLM-R 기준 1토큰 ≈ 1.6자) |
| 오버랩 | 15% (~128자) |
| 최소 크기 | 200자 미만 청크는 인접 청크에 병합 |
| 접두 | `제목 > 헤딩1 > 헤딩2\n` |
| 최대 | 섹션이 매우 길면 문단 단위로 분할하되 헤딩 경로는 유지 |

p10이 336자이므로 **전체 문서의 10% 이상은 단일 청크**가 된다. 짧은 문서를 억지로 쪼개지 않는다.

## 7. 검색

### 7.1 3단 검색

```
질의
 ├─▶ dense 검색  (Qdrant, top-100)
 └─▶ sparse 검색 (Qdrant, top-100)
        │
        ▼
   RRF 융합 (k=60) → top-100
        │
        ▼
   리랭커 (bge-reranker-v2-m3) → top-8
        │
        ▼
   LLM 답변 생성 (근거 문단 + 출처 링크)
```

RRF(Reciprocal Rank Fusion)를 쓰는 이유는 dense·sparse 점수 스케일이 달라 단순 가중합이 불안정하기 때문이다.

### 7.2 모델 선정 (Phase 0에서 확정)

§2.8의 이해충돌 우려 때문에 벤치마크 수치만으로 확정하지 않는다. 후보:

| 역할 | 후보 |
|---|---|
| dense | `nlpai-lab/KURE-v1` (MIT) vs `telepix/PIXIE-Rune-Preview` (Apache 2.0) vs `BAAI/bge-m3` |
| sparse | `telepix/PIXIE-Splade-v1.5` (0.1B) vs Qdrant 내장 BM25 |
| reranker | `BAAI/bge-reranker-v2-m3` vs `telepix/PIXIE-Spell-Reranker-Preview-0.6B` |

**Phase 0 평가 절차:** 나무위키 문서 1만 건을 색인하고, 나무위키 내용에 대한 질의 100개(정답 문서 라벨 포함)로 Recall@10과 NDCG@10을 측정해 확정한다.

### 7.3 VRAM 배치 (6GB)

| 시점 | 상주 모델 | 추정 VRAM |
|---|---|---:|
| 색인 시 | dense 0.5B (fp16) + sparse 0.1B (fp16) | ~1.4 GB + 배치 활성값 |
| 질의 시 | + reranker 0.5B (fp16) | ~2.6 GB |

6GB 안에 셋 다 상주 가능하다. 배치 크기는 Phase 0 벤치마크로 확정한다.

### 7.4 답변 생성

교체 가능한 인터페이스 뒤에 둔다. 기본은 **로컬 LLM (Ollama, 4B급 4bit)** 으로 비용 0을 유지한다. 데이터가 CC BY-NC-SA(비영리)이므로 유료 API를 붙일 사업적 이유가 없다.

**출처 표기는 선택이 아니라 라이선스 의무다.** 모든 답변에 원문 문서 링크와 CC BY-NC-SA 2.0 KR 고지를 포함한다.

## 8. 장애 복구와 재처리

| 시나리오 | 대응 |
|---|---|
| 파서 로직 수정 | `docs.raw`를 오프셋 0부터 재생. **재크롤 불필요** |
| 임베딩 모델 교체 | `chunks.ready`를 오프셋 0부터 재생. **재크롤·재파싱 불필요** |
| 청킹 전략 변경 | `docs.raw` 재생 (블롭 저장소가 원본 HTML 보유) |
| 임베더 크래시 | 컨슈머 그룹이 파티션 재배정. 미커밋 오프셋부터 재개 |
| 크롤러 크래시 | `crawl_state.next_due_at`에서 재개 |
| 중복 수신 | `content_hash` 동일 시 조기 반환. `chunk_id` upsert로 멱등 |
| 추출기 무성 실패 | §6.2 카나리아가 감지 후 파서 정지 |
| 상대 서버 부하 | 서킷 브레이커 (429/5xx 10회/분 → 10분 정지) |

**멱등성이 이 설계의 핵심 안전장치다.** 모든 재처리는 "토픽을 처음부터 다시 읽는다"로 환원된다.

## 12. 구현 실측 (2026-08-31 추가)

Phase 0~1을 실제로 구현하면서 설계 가정 몇 개가 뒤집혔다.

### 12.1 임베딩 처리량 — 추정치의 2~3배

| 모델 | batch 16 | batch 32 | 900만 청크 환산 |
|---|---:|---:|---:|
| nlpai-lab/KURE-v1 | 17.6 청크/s | 4.0 청크/s | **142시간** |
| telepix/PIXIE-Rune-Preview | 23.3 청크/s | (미완) | **107시간** |

설계 §5의 추정치는 30~60시간이었으나 **실측은 107~142시간(4.5~6일)** 이다.

> ⚠ **이 수치는 오염되었다.** 측정 중 같은 GPU에서 사용자의 강화학습 훈련이
> 약 2.9GB를 점유한 채 돌고 있었다. batch 32가 batch 16보다 4배 느린 비정상
> 결과도 이 경합 때문으로 보인다. **하한선으로만 취급하고, GPU가 유휴일 때
> 재측정해야 한다.**

가용 VRAM은 6GB 전부가 아니라 **약 3GB**로 잡아야 한다.

### 12.2 dense vs sparse 비용 분리 (중요)

임베딩 시간의 대부분은 dense가 아니라 **sparse**가 쓴다. 청크 32개(평균 435자)를
GPU에서 분리 측정한 결과:

| | 처리량 | peak VRAM | 시간 비중 |
|---|---:|---:|---:|
| dense (KURE-v1, 0.5B) | 51.8 청크/s | 2,654 MB | 17% |
| **sparse (PIXIE-Splade, 0.1B)** | **10.8 청크/s** | 1,576 MB | **83%** |
| 합산 | 8.95 청크/s | — | — |

**파라미터가 5분의 1인 모델이 시간의 83%를 쓴다.** 이유는 파라미터 수가 아니라
출력 차원이다. MLM 헤드가 어휘 25만 차원 로짓 `(배치 × 길이 × 250,002)`를 내놓고,
그 텐서 자체가 연산과 메모리 대역폭을 지배한다.

최적화 여지 (미착수):
- sparse의 `max_length`를 512 → 256으로 줄이면 비용이 절반. 어휘 신호는
  문서 앞부분에 몰려 있어 손실이 작을 가능성이 있다. **측정 후 결정할 것.**
- Qdrant 내장 BM25로 대체하면 sparse 모델이 아예 사라진다. 다만 품질이
  BM25 0.5071 vs SPLADE 0.7670으로 크게 떨어진다.

### 12.3 확정된 설정

- `max_seq_length`를 **8192 → 512**로 낮춘다. BGE-M3 계열의 기본값은 8192인데
  청커가 850자(≈512토큰)로 자르므로 그 이상은 어텐션 비용 낭비다.
- dense 배치 **16**. 이 하드웨어에서 32는 오히려 크게 느려진다.
- **sparse 배치 2.** 로짓 텐서가 `(배치 × 길이 × 250,002)`라 배치 16이면
  RAM 8.7GB를 점유해 머신 전체가 느려진다 (실측).
- SPLADE 구현 시 `log1p(relu(·))`는 단조증가라 max 풀링과 교환된다.
  변환을 `(B, L, V)`가 아니라 풀링 후 `(B, V)`에 적용하면 거대 텐서가
  3벌에서 1벌로 준다.

### 12.4 구현 중 드러난 함정

| 증상 | 원인 | 대응 |
|---|---|---|
| 컨슈머 그룹이 0건만 반환 | **kafka-python이 Python 3.14의 selectors와 비호환** (`Invalid file descriptor: -1`) | confluent-kafka(librdkafka)로 교체 |
| 블롭에 HTML 대신 압축 바이너리 저장 | `Accept-Encoding`에 `br`을 직접 넣었는데 httpx에 brotli 디코더가 없었음 | 헤더를 직접 지정하지 않는다. 응답이 HTML인지 검증하는 가드 추가 |
| 문서 15건이 색인 실패 | 추출 텍스트의 NUL(0x00) — PostgreSQL text가 거부 | 추출 단계에서 제어문자 제거 |
| 크롤 요청이 전부 실패 | User-Agent에 한글 — HTTP 헤더는 ASCII만 | UA를 ASCII로 |
| 두 번째 배치부터 크래시 | `asyncio.Lock`이 `asyncio.run()`마다 새로 생기는 루프에 묶임 | 락 없이 슬롯 예약 방식으로 |
| 카나리아가 매번 오경보 | 기준선이 0인 상태로 비교 | 첫 성공 파싱을 기준선으로 자동 확립 |
| 카나리아가 영영 재검증 안 됨 | 문서가 안 바뀌면 "변경 없음" 단축 경로를 타서 검사 자체가 실행되지 않음 | 카나리아 문서는 단축 경로 예외 |
| **가장 큰 문서 15개가 조용히 누락** | 문서 행과 청크를 따로 커밋해서, 청크 INSERT만 실패하면 청크 없는 문서가 남음. 재파싱 때 해시가 같아 건너뛰어 **영구 손실** | ① 한 트랜잭션으로 커밋 ② "변경 없음" 판정에 `has_chunks` 조건 추가 ③ 스모크 테스트에 탐지 추가 ④ `repair_chunkless.py`로 블롭에서 복구 |
| **임베딩이 조용히 멈춤** | 배치 128개 처리 중 다른 작업과 경합해 `max.poll.interval.ms`(15분)를 초과 → Kafka가 컨슈머를 그룹에서 축출. 크래시가 아니라 진행만 멈춰서 알아채기 어려움 | `FLUSH_EVERY`를 128 → **32**로 축소해 한 사이클을 10초 내외로 유지 |

`torch`는 CUDA 빌드를 **먼저** 설치해야 한다. `sentence-transformers`가 PyPI에서
더 높은 버전 번호의 CPU 빌드를 끌어오면 pip이 교체하지 않는다.

### 12.5 Phase 1 실측 결과

## 13. 지식그래프 확장 (2026-08-31 추가)

나무위키는 지식그래프 소재로 적합하고, 재료를 이미 수집하고 있다.

| 그래프 구성요소 | 나무위키에서 | 상태 |
|---|---|---|
| 노드 | 문서 124만 | 수집 중 |
| 엣지 | 내부 링크 — **실측 문서당 441~817개** | `documents.outlinks`에 저장 |
| 타입/온톨로지 | 분류 232,870개 | `documents.categories`에 저장 |

전체 엣지는 약 10억 개로 추정된다. 별도 엣지 테이블은 sha1 40자 × 2 × 10억 =
80GB로 과하므로 **`TEXT[]` 배열 + GIN 인덱스**로 둔다. TOAST 압축이 먹고
역링크 질의(`WHERE outlinks @> ARRAY['김연아']`)도 된다.

### 13.1 로드맵 — 3단계 전부 수행한다 (확정)

사용자 결정: 아래 3단계를 모두 구현한다. 순서와 선행 조건은 아래와 같다.

---

#### KG-1. 문서 그래프 — **구현됨**

링크와 분류를 저장하고 검색에 활용한다.

| 항목 | 상태 |
|---|---|
| `documents.outlinks TEXT[]` + GIN 인덱스 | ✅ |
| `documents.categories TEXT[]` + GIN 인덱스 | ✅ |
| `GET /api/graph?title=` — 이웃·역링크·분류 | ✅ |
| `GET /api/search?expand=true` — 상호 링크 이웃 확장 검색 | ✅ |
| **PageRank** — 링크 중심성을 검색 순위·크롤 우선순위에 반영 | ⬜ 미착수 |

상호 링크(서로 가리키는 쌍)만 이웃으로 취한다. 문서당 링크가 400~800개라
단순 이웃은 너무 넓다.

PageRank 구현 메모: 10억 엣지를 메모리에 올릴 수 없으므로 `outlinks`를
int32 인접 리스트로 한 번 덤프한 뒤(약 8GB) 반복 계산한다. 결과는
`documents.pagerank REAL` 컬럼에 저장하고 RRF 융합 후 가중치로 쓴다.

---

#### KG-2. 관계 추출 — 미착수 · **2026-08-31 전면 재설계**

> **원래 계획(LLM 트리플 추출)은 기각했다.** 사용자의 선행 프로젝트
> [kasangyong/ontology](https://github.com/kasangyong/ontology)가 정확히 그 경로에서
> 실패한 기록을 남겼기 때문이다. 아래 §13.2 참조.

**바뀐 원칙: 규칙으로 뽑히는 관계만 먼저 판다.**

나무위키에는 LLM 없이 결정론적으로 추출되는 관계가 링크 말고도 4종 더 있다:

| 소스 | 얻는 관계 | 추출 방식 | 규모 |
|---|---|---|---|
| **링크** (KG-1에서 이미 확보) | `LINKS_TO` (무타입) | HTML `href` | 문서당 509개 실측 |
| **틀 = 인포박스** | `수도`·`인구`·`설립일`·`소속` 등 **타입 있는 관계** | key-value 파싱 | 틀 103,689개 |
| **분류** | `IS_A` / 타입 체계 | 이미 `categories`에 수집 중 | 232,870개 |
| **문서 제목 `A/B`** | `PART_OF` (`김연아/선수 경력` → `김연아`) | 문자열 규칙 | 다수 |
| **리다이렉트** | `SAME_AS` / 별칭 | 결정론적 | 전체 문서의 34.4% |

**인포박스가 핵심이다.** 링크만으로는 "관련 있다"밖에 말하지 못하는데(선행
프로젝트가 패키지 의존성에 대해 지적한 "관계 유형이 하나뿐" 한계와 동일),
인포박스는 타입 있는 관계를 준다. DBpedia가 위키백과로 한 것이 정확히 이것이다.

**LLM 트리플 추출은 이 4종을 다 소진한 뒤에 재검토한다.** 하기로 한다면
근거 청크를 반드시 함께 저장한다 — 근거 없는 트리플은 환각과 구분되지 않는다.

**선행 조건**: 인포박스 추출 가능성 기술 검증 (틀 HTML에서 key-value가 실제로
안정적으로 나오는지). 안 되면 KG-2를 다시 설계해야 한다.

---

#### KG-3. 커뮤니티 요약 (GraphRAG 방식) — 미착수

그래프를 클러스터링하고 계층 요약을 만들어 **전역 질의**에 답한다.
("나무위키에서 한국 현대사는 대체로 어떻게 서술되나?" 같은 질문)

- **선행 조건**: KG-2 완료
- **왜 필요한가**: 벡터 검색은 국소 질의(특정 사실 찾기)에 강하고 전역 질의에
  약하다. 상위 k개 청크만 보기 때문이다. 커뮤니티 요약이 그 약점을 메운다.
- **절차**: Leiden 등으로 그래프 커뮤니티 탐지 → 커뮤니티별 LLM 요약 →
  요약을 계층으로 쌓음 → 전역 질의는 요약 계층에서 답하고 국소 질의는
  기존 벡터 검색으로 답하는 **라우팅**을 둔다.
- **비용**: 셋 중 최대. 커뮤니티 수만큼 LLM 요약이 필요하고, 그래프가
  갱신될 때마다 영향받은 커뮤니티를 다시 요약해야 한다.
- **주의**: 나무위키는 하루 33,600개 문서가 바뀐다. 요약을 매번 전부 다시
  만들 수 없으므로 **변경된 커뮤니티만 무효화하는 증분 갱신**이 필수다.
  이 설계 없이 시작하면 KG-3은 유지 불가능해진다.

## 13.1.0 리다이렉트 접기 — 구현됨 (2026-08-31)

**증상**: 추출 수율 카나리아가 `파이썬`에 대해 -41.8% 이탈을 경보했다.
다른 카나리아 4개는 ±0.0%였으므로 추출기 문제가 아니었다.

**원인**: `파이썬`은 `Python`으로 가는 리다이렉트다. 크롤러가
`follow_redirects=True`로 따라가므로 **정식 문서의 내용이 별칭 제목으로 저장**된다.
표본 300개 조사 결과 **5.3%**가 이 상태였고, 전수 검사에서 **255개(5.2%)** 로 확인됐다.

```
저장 '픽사'          → 실제 H1 '픽사 애니메이션 스튜디오'
저장 '3.1절'         → 실제 H1 '삼일절'
저장 '2016 리우 올림픽' → 실제 H1 '2016 리우데자네이루 올림픽'
```

**피해 세 가지**

1. **중복 임베딩.** 별칭과 정식 제목이 둘 다 수집되면 같은 내용을 두 번
   임베딩한다. GPU가 유일한 병목인 파이프라인에서 직접적인 손해다.
   (실제로 69건이 이미 중복 상태였다)
2. **그래프 분절.** `픽사`와 `픽사 애니메이션 스튜디오`가 별개 노드가 되어
   PageRank 중심성이 나뉜다.
3. **검색 중복.** 같은 문단이 결과에 두 번 나온다.

**대응** — 설계 §13.1 KG-2의 `SAME_AS`를 앞당겨 구현했다.

| 위치 | 내용 |
|---|---|
| `redirects(alias, canonical)` 테이블 | 별칭 관계 저장 |
| 파서 | `<h1>`이 요청 제목과 다르면 **정식 제목을 문서 정체성으로** 삼고 별칭을 기록 |
| `scripts/fold_redirects.py` | 이미 저장된 문서를 블롭에서 재추출해 접는다 (재크롤 불필요) |
| `scripts/pagerank.py` | 별칭 링크를 정식 노드로 해석 |

판별 기준은 페이지의 `<h1>` 제목이다. 나무위키는 리다이렉트를 따라간 뒤에도
**정식 제목을 `<h1>`에 표시**하므로 신뢰할 수 있다.

> 카나리아가 없었으면 못 찾았을 문제다. 오류가 나지 않고 데이터만 조용히
> 중복되는 종류였다 (설계 §6.2의 존재 이유).

## 13.1.1 알려진 한계 — 크롬 링크 오염 (2026-08-31)

PageRank 상위에 `편집 요청`(5위)과 `크리에이티브 커먼즈 라이선스`(6위)가 올라온다.
둘 다 실제 문서이긴 하지만(각 10,657자 / 28,202자), 링크하는 쪽이
`과학고등학교`·`부촌`·`중졸`·`한국 록`·`아인슈타인` 처럼 **주제상 전혀 무관**하다.
즉 본문이 아니라 **페이지 UI에서 나온 링크**다.

`편집 요청` 링크는 문서 상단 13KB 지점의 "편집 권한이 부족합니다 …
[편집 요청 도움말]" 안내 패널에 있다. 보호된 문서에만 나타나서 전체의
16.3%에서 관측된다.

**고치지 않기로 한 이유.** 링크 수확 범위를 본문(`html[start:end]`)으로 좁히면
툴바는 빠지지만 **인포박스도 함께 빠진다** — 첫 섹션 앵커보다 위에 있기 때문이다
(실측: 대한민국 링크 1,468 → 839개, 사라진 것에 `.kr`·`1987년`·`24절기`
같은 인포박스 링크가 포함). 인포박스는 KG-2에서 타입 있는 관계를 주는
**가장 값어치 있는 소스**라, 툴바 링크 몇 종 제거하려고 버릴 수 없다.

**대신 나중에 통계로 거른다.** 코퍼스가 커지면 크롬 링크는 저절로 드러난다 —
주제적으로 무관한 문서들이 일제히 가리키는 대상이기 때문이다. 판별 기준
후보: ① 문서의 N% 이상이 링크 ② 링크하는 문서들의 분류가 서로 무관.
지금 4,927문서 규모에서는 50% 이상 링크되는 대상이 `대한민국`(64.4%, 정상)
하나뿐이라 통계적 판별이 아직 이르다.

관련 코드: `ExtractedDoc.body_html`(본문 텍스트용)과 `link_html`(링크 수확용)을
분리해 두었다. 판별 기준이 정해지면 `link_html` 쪽만 좁히면 된다.

## 13.1.2 프런티어 우선순위 — BFS는 가치 순서가 아니다 (2026-09-07)

**증상**: 코퍼스를 5천 → 5만 문서로 늘리던 중 404율이 2% → 11%로 올랐다.
404가 난 제목을 보니 전부 윤충(rotifer) 종 이름이었다.

```
긴다리타원안갑윤충 · 고깔협관윤충 · 두각추돌기협관윤충
필로디나 운둘라타 · 트리코케르카 콜라리스
```

**원인**: BFS가 생물 분류 목록 문서 하나에 걸려, 거기 나열된 수백 개
빨간 링크(존재하지 않는 문서)를 프런티어에 넣고 그대로 크롤하고 있었다.
**BFS의 발견 순서는 가치 순서가 아니다.**

당시 프런티어의 인링크 분포를 재보니 문제가 분명했다:

| 인링크 | 미수집 문서 수 |
|---:|---:|
| 50개 이상 | 9,766 |
| 20개 이상 | 25,255 |
| 1개 | 약 22만 ← **여기를 긁고 있었다** |

**대응**: `scripts/prioritize_frontier.py` — 인링크 수로 프런티어를 정렬한다.
여러 문서가 가리키는 제목은 실재할 가능성도, 검색될 가능성도 높다.

**PageRank를 쓰지 않는 이유**: PageRank는 **이미 수집한** 문서에만 값이 있다.
아직 수집하지 않은 프런티어 항목의 순서를 정하는 문제라 인링크 수가 맞다.

적용 후 다음 크롤 대상이 바뀌었다:

```
전: 긴다리타원안갑윤충, 트리코케르카 콜라리스 …
후: 홍콩(621), 2003년(556), 한국-브라질 관계(549), 청나라(457)
```

> **구현 함정**: 티어를 높은 문턱부터(50+ → 20+ → …) 적용하면 뒤이은 낮은
> 문턱이 같은 행을 덮어써서 **가장 느슨한 티어가 이긴다.** 인링크 621개인
> `홍콩`이 최하위 등급을 받았다. 낮은 문턱부터 적용해야 한다.

## 13.2 선행 프로젝트에서 가져온 것 (2026-08-31)

사용자의 [kasangyong/ontology](https://github.com/kasangyong/ontology)는 넉 달간
지식그래프·GraphRAG를 실측한 기록이다. 결론과 실패가 모두 남아 있어 그대로
전용할 수 있다.

### 가장 중요한 한 줄

> **"성패를 가르는 것 하나 — 관계를 어디서 얻는가. 규칙으로 뽑히면 성공,
> 산문이면 LLM이 필요하고 비싸고 정밀도가 낮다."** (`docs/rag-lessons.md` §3)

그 프로젝트의 코퍼스 판정표:

| 데이터 성격 | 관계 추출 | 판정 |
|---|---|---|
| 논문 인용망, 패키지 의존성, 코드베이스, 법령 | 결정론적 | ✅ |
| 정형 표가 있는 문서 | 표 모양에 의존 | ⚠️ |
| **일반 산문** | LLM 필요 | **❌ 비싸고 정밀도 낮음** |

그 프로젝트는 문서 코퍼스(산문)로 시작해 **관계 46개**에서 막혔고, 로컬 LLM
관계 추출은 **recall 25%**로 실패했다. 코퍼스를 인용망으로 바꾸자 같은
파이프라인에서 관계 **634개**, 다중홉 후보 **1 → 332개**가 됐다.

### 나무위키에 적용하면

**나무위키 링크망이 그 "인용망" 자리다.** HTML `href`에서 100% 결정론적으로
뽑히고, 문서 2,071개만으로 이미 엣지 106만 개다(전수 시 약 10억 추정).
그 프로젝트를 넉 달 막았던 "그래프가 너무 작다"는 병목이 여기엔 없다.

반대로 **나무위키 본문은 "일반 산문"이므로 ❌ 칸이다.** 그래서 KG-2를
규칙 기반으로 전면 재설계했다 (§13.1).

### 채택한 원칙 6개

1. **경쟁 질문(골든셋)이 스키마보다 먼저다.** 골든셋이 요구하지 않는
   클래스·관계는 만들지 않는다.
2. **2층 그래프.** 도메인 층(엔티티)과 렉시컬 층(`Chunk` + 임베딩)을 분리하고
   `MENTIONS`로 잇는다. 현재 구조(Postgres `chunks` + Qdrant)가 이미 렉시컬
   층이므로 도메인 층만 얹으면 된다.
3. **클래스 ≤ 7.** 판정 기준은 *"자체적으로 관계를 가지면 클래스, 단순 값이면
   속성"*. 애매한 항목은 판정 근거를 문서에 남긴다.
4. **관계마다 원문 인용.** 모든 관계에 근거 문장과 출처를 붙인다.
   나무위키는 스스로 검증되지 않았다고 고지하는 소스라 이게 더 중요하다.
5. **LLM 없는 평가 하네스 + 유의성 검정.** 평균만 비교하지 않는다.
   표본 크기를 미리 계산한다 (그 프로젝트는 22문항으로 검정력이 없어
   대표 수치를 스스로 철회했다).
6. **실패도 리포트에 남긴다.**

### 믿지 않기로 한 것

그 프로젝트가 **반증하거나 미검증으로 내린** 주장들이다. 이 프로젝트에서도
전제로 삼지 않는다:

- "그래프가 벡터를 이긴다"
- "라우터가 검색을 개선한다"

## 13.3 인과 추론의 범위 (2026-08-31)

"사건을 입력하면 왜 일어났는지" 같은 질문에 대한 정직한 경계.

**되는 것**
- 나무위키에 인과가 **서술되어 있으면**, 링크망을 따라 `사건 → 배경 → 그 배경의
  원인`까지 다단계로 근거를 모으고 LLM이 서술로 정리한다.
- 벡터 검색만으로는 상위 k개 청크만 보므로 이 다단계 추적이 안 된다.
  **그래프의 값어치가 정확히 여기 있다.**

**안 되는 것**
- 나무위키에 없는 인과는 만들 수 없다. 없으면 LLM이 지어낸다.
- **인과 관계 자체를 산문에서 뽑는 것은 §13.2의 ❌ 칸이다.** 링크는
  "관련 있다"만 말하고 "때문이다"는 말하지 않는다.
- 나무위키는 *"검증되지 않았거나 편향적이거나 잘못된 서술이 있을 수 있다"* 고
  스스로 고지한다. **편향된 인과 서술을 그래프로 만들면 편향을 구조화하게 된다.**

**따라서 이 기능은 "추론"이 아니라 "근거 수집 + LLM 서술"로 부른다.**
안전장치는 원칙 4(관계마다 원문 인용)다. 답변이 "A 때문에 B"라고 하면 근거
문장과 문서 링크를 함께 제시하고, 근거가 없으면 기권한다.

## 13.4 그래프 저장소 결정 (2026-08-31)

**Neo4j를 도입한다.** 선행 프로젝트의 Cypher 레시피·스키마 제약·2층 그래프
패턴을 그대로 재사용할 수 있다는 점이 결정 근거다.

미해결 과제:

- Neo4j Community는 엣지 10억 개를 감당하기 어렵다. **전체 링크망은 Postgres에
  두고, PageRank 상위 문서 + 인포박스 관계만 Neo4j로 내려 도메인 층을 쌓는**
  분할 전략이 필요하다. 경계선을 어디에 그을지는 미정.
- 벡터 인덱스를 Qdrant에 둘지 Neo4j로 합칠지 미정. 선행 프로젝트는 Neo4j
  벡터 인덱스(1024차원)를 썼고, 현재 시스템은 Qdrant를 쓴다. 이중화보다
  한쪽으로 모으는 게 낫지만, Qdrant의 sparse 하이브리드를 포기해야 한다.

## 14. 미해결 사항

1. **GPU 유휴 상태에서의 임베딩 처리량 재측정** — §12.1의 수치는 경합 상태 하한선이다.
2. **모델 품질 A/B** — PIXIE 계열이 유리하다는 벤치마크는 이해충돌 우려가 있다.
   나무위키 질의 100개로 직접 평가해야 한다. 처리량은 PIXIE-Rune-Preview가
   KURE-v1보다 32% 빠른 것이 자체 측정으로 확인됐다.
3. **BFS 수렴 홉 수** — 몇 홉에 124만을 덮는지는 전수 크롤 전까지 알 수 없다.
4. **조건부 요청 지원 여부** — 나무위키의 `ETag`/`If-Modified-Since` 지원 미확인.
5. **답변 생성 LLM 선정** — 미착수.
